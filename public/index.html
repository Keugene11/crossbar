crossbar

An OpenRouter-style LLM routing gateway. One API key, one wire format, many providers, with policy routing and failover.

Speak the OpenAI Chat Completions API, name a model as provider/model, and crossbar picks an upstream endpoint by policy, translates into that provider's native dialect, streams the response back re-normalized, cascades to the next candidate on failure, and books tokens and cost.

Try it

curl https://crossbar.vercel.app/v1/models \
  -H "Authorization: Bearer $CROSSBAR_KEY"

Endpoints

POST /v1/chat/completionsCompletions, buffered or streaming
POST /v1/completionsLegacy text completions
GET  /v1/modelsCatalog with per-endpoint pricing
GET  /v1/providersProviders and their data-retention policy
GET  /v1/generation?id=Tokens, cost, and the full attempt list
GET  /v1/keyThis key's usage and rate limit
GET  /v1/activityDaily usage by model and provider
GET  /healthLiveness and readiness (no auth)

Routing

With no sort given, endpoints that failed in the last 30 seconds are deprioritised, then the rest are ordered by inverse-square price weighting — a $1/MTok endpoint is roughly 9× more likely to be tried first than a $3/MTok one. Whatever remains becomes the fallback chain.

One invariant shapes the cascade: once a byte reaches the client, no other endpoint can be tried. Failures before the first chunk fall through to the next candidate; failures after it become a terminal frame inside the open stream, never a silently truncated answer.

This deployment

Runs in stateless mode: the catalog is compiled in and the ledger lives in memory for the life of the instance, so /v1/generation and /v1/activity only see traffic from the instance that served it. No upstream provider keys are configured here, so chat requests reach the provider and come back 401 — the routing, translation, failover and accounting paths are all real, the credentials are not.
